# Experimental cooperative Strength in original Fiery Path

Default off. Native parent #121 (414fa149b58b5caa5aa75271fab040e272d6d217), app parent #483 (8c66de2e449cd18591daaab0c40bf41b4565a60b). Independent of Maya's integration and all held recovery/relay writes.

## Player experience

Two tagged friends enter original Fiery Path with its six original boulders unmoved. Each opens the existing partner interaction menu and chooses **Share boulder pushes**. The menu indicates waiting for the friend or sharing on. Registration expires after roughly twelve seconds without a match; retry enrollment together if needed. The native adapter refuses admission if a boulder has already moved, a reviewed object is missing/changed, a temporary hide flag is set, a movement is active, or the engine cannot allocate all six objects.

The player who actually activated native Strength pushes an original boulder normally. Both clients briefly lock field controls and independently check the same boulder layout and destination. Both must acknowledge before either moves. Each executes an actual native slow held-movement step; only after both report its exact completion are controls released. The companion does not run Strength scripts or receive a badge/HM/story flag. Toxic/Fire Stone remain ordinary private pickups. No progress/reward claims are produced.

The six boulders remain instantiated while enrolled, preventing independent camera despawn/reset. No save object-template coordinates are rewritten. Turning sharing off or leaving resumes stock map lifetime. The system does not make the puzzle permanent, reset it for another player, or share it with nonparticipants. Native eligibility/collision still governs the performer. Only normal destination metatiles are accepted, excluding all warp coordinates; other Strength caves, switches, holes, Rock Smash and generated terrain are not supported.

## Failure and limits

Wrong owner/tag/visit/revision, mismatched layout, occupied destination, concurrent proposals, timeout, missing applied acknowledgment or departure cannot count as success. A committed in-flight native step finishes rather than being reversed through a possibly occupied tile; then sharing closes. A partial outcome remains the actual local state, never fabricated completion. Re-enter with matching initial layouts to enroll again. No real save was used.

This is a source-wired **draft**, not a rendered/linked playtest. Seven focused tests pass: Python transaction/transport checks plus actual native C adapter/client execution against synthetic engine objects under UBSan. Both new native modules pass syntax checks with recovered headers, feature on/off. Full world_activity/link_transport compilation is blocked by incomplete recovered include dependencies. Full exact-head native link, actual map sprites/capacity/animation timing, two-client latency/disconnect, menu readability and ordinary-game regression QA remain mandatory. There is no native dust/sound embellishment beyond the actual existing held-movement animation. Waiting/failure feedback is currently the menu state, not a field popup.

## Enable only for development QA

Build with `--development --experimental-shared-strength` (EW_SHARED_STRENGTH=1); default is zero. Both clients and the matching app server are required. A mixed old client/server will not enroll successfully; it is not silently treated as a participating friend. The old two-player battle path is unchanged.
