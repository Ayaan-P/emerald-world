# Experimental shared generated cave

This draft is stacked on the native generated-cave prototype. `GENERATED_MAP_READY` remains 0. It is not an integrated release and does not claim a real two-client game has worked.

A standalone authority can be started explicitly with `--generated-cave-template cave.bin`, using the exporter from the parent draft. It reads and validates the bounded template at startup. The normal launcher and hosted-service setup do not yet expose this option. A local owner can replace the cave in memory through the existing private admin socket, only when no connected trainer is known to be inside; the server never accepts cave publication from a player connection.

A feature-capable presence client negotiates a cave capability during authenticated HELLO. An older server can reject that capability and the client falls back to the existing role. When a cave exists, the server sends the same versioned grid and SHA-256 identity to each authenticated requesting client. The native client checks every frame, recomputes the hash, validates closed boundaries, connectivity and entrance/exit geometry, then acknowledges that exact ID. The server will not accept generated-cave presence without this connection's acknowledgment or on a wall. On reconnect, the client suppresses cave presence until it has revalidated and acknowledged the authority's cave. If the authority offers different geometry or no cave, the client tries to leave the old instance before acknowledging another, including when reconnection happens during the entry fade. Entry and both exit paths check warp-task capacity first. The client refuses the local `--generated-map` override while connected to a world.

Peers in the same generated cave can appear in ordinary native presence snapshots. Generated-cave peers are omitted from the Fly-to-friend roster and from legacy clients' initial generic snapshots. Mutable world-mechanic tiles and objects cannot target the reserved cave. The native World menu, server link-presence view and invitation guards disable trade, PvP, tag and ordinary trainer interactions in the cave; entry is refused while tagged, holding an invitation, or participating in a story rally; the authority also excludes cave presence from rally eligibility. Chat and other existing world infrastructure are not newly certified here.

The prototype is limited to one current cave per authority process. A replacement is ephemeral and is not retained across restart. It does not yet create multiple map instances, call an LLM, generate tileset art, populate encounters/NPCs/items, or persist a player inside it. It does not claim safe concurrent spawn placement: both clients currently enter at the same tile, and crowded one-tile corridors or occupied return tiles need a real design. The local return point is captured on entry, but return safety, disconnect timing, scripts and all save paths have not been verified in actual gameplay. The existing save guard remains in place. A restart with changed template causes clients to attempt return, not migrate in place; actual network interruption and recovery remain untested.

Focused tests use the production server dispatch, cave authority, native SHA/framing, native handshake/return state machine and generated-map staging with disposable stubs. Tests cover two authenticated in-memory sessions, legacy snapshot isolation, unauthorized upload/entry, wall rejection, same-map peer projection, mismatched reconnect, invitation and presence suppression, 40 SHA comparisons with Python, and the existing 14 story-rally coordinator tests. `test_shared_cave_socket.py` is a two-connection Unix-socket protocol test; it has been syntax-checked but **not run** here because this environment denied local socket creation. No real two-client native, WAN, rendering, gameplay, save/reload or online acceptance has been performed. The isolated gate-on and gate-off C syntax checks do not substitute for a native build. The main-baseline workflow lists the new tests for the combined candidate.

Before enabling: implement or verify safe concurrent spawn, path congestion and return on occupied/changed tiles; audit interactions and all persistence paths; exercise the actual socket test and two native clients, including simultaneous entry, stale snapshots, disconnect, changed and missing authority cave, malformed/fragmented frames, reconnect, safe return, private-party/inventory preservation and save/reload. Reconcile map IDs and regenerate the map catalog with the integration candidate. This prototype must not be deployed or merged as an accepted multiplayer feature without those checks.

## Live host replacement

`python3 -m world.publish_cave --admin-socket /path/to/admin.sock cave.bin` submits a validated inert template through the authority's existing owner-only local Unix socket. The server independently validates the complete 969-byte input and refuses changes while any connected peer is known to be in the generated cave. A same-content publication is a no-op. Invalid input, occupancy or output-queue backpressure leave the existing cave unchanged. This API is not available on player or control connections; the admin socket retains its existing filesystem permissions. The normal launcher and hosted service do not yet expose this control.

The server revokes existing cave acknowledgments and sends a reset to capable clients, which re-fetch and revalidate before publishing cave presence. A reset racing an in-flight GET, ACK or entry fade is handled without treating the old map as the new one; an affected player who already entered the old geometry is sent back before the new layout is acknowledged. Existing visitors are not forcibly displaced by an accepted host update: publication is refused while their presence is known. Disconnects, unreported entry, occupied return tiles, safe concurrent spawning, queue failure and other real-network behavior still need full native acceptance. Replacement is held in memory only; restart returns to the configured startup template. It does not call a model.
