# Voluntary cooperation between independent world characters

This app-only candidate adds reusable work requests to the discovered capability
runtime. It is not a new authored quest, named-character arc, remote-control
mechanism, or native simulation. It builds on #336 and keeps native #40 pinned.
It contains none of the unpublished doubles work.

## Connected experience

Two generated characters actually meet on the same admitted map revision. One
uses `world.request_cooperation` to express a public fictional purpose and an
exact completion predicate over an existing tool's successful result. The other
receives a committed event through its existing configured author queue and
independently accepts, declines or ignores it. Accepting never installs a plan.

The recipient chooses its own plan and existing actions, including navigation,
world authoring, object use, or an optional player-facing service. All existing
preconditions remain in force. It can then use `world.deliver_cooperation` with
that action's successful receipt, including the normal `tool_receipt` result
reference in the same multi-step plan. The authority validates actor, tool,
post-acceptance time and exact typed result fields. The requester receives a real
public event and may revise its next plan. Nothing automatically increases trust,
grants rewards, rewrites parties, or claims the prose purpose was achieved.

For example, tests have a recipient independently choose an ordinary native
retail catalog or move-tutor opportunity, then deliver the actual configuration
receipt. Players still choose purchases/party members in the already implemented
native menus. These are tests of general composition, not built-in character
stories. No sale or learned move is inferred.

## General interface

- `world.request_cooperation(target,purpose,tool,where)`: adjacent idle generated
  actors only. Purpose is public literal text (120 characters). `where` is compact
  JSON (350 characters), with `outcome` and up to three other scalar result fields.
  Only discovered world-actor capabilities qualify; cooperation cannot recursively
  demand more cooperation. One unresolved request per unordered actor pair.
- `world.respond_cooperation(request,decision)`: recipient accept/decline/abandon;
  sender withdraw. Acceptance can be remote after the real meeting. Requests are
  durable communication, not fictional ongoing physical meetings.
- `world.deliver_cooperation(request,receipt)`: recipient supplies an actual
  successful authority result after acceptance. Delivery means that historical
  operation matched the predicate, not that state is unchanged today or a model's
  narrative is true. Pending, blocked, old, other-actor and fabricated records do
  not qualify.

Discovery exposes active requests and frozen terms to the configured author.
Terminal requests remain durable with public causal events; there is no lifetime
request ceiling. Sender withdrawal or recipient abandonment stops the agreement,
not actions already committed by the recipient. Changes and the runtime receipt
share a transaction. No extra provider process or model spend is enabled here.
Peer requests are explicitly fictional speech, never operator authorization.

## Boundaries and verification

Generated actors only, not remote relocation/control of original Hoenn cast.
No new native code or save format; original services/story stay unchanged.
The component suite checks independent reaction enrollment, actual authority
execution, native service transport rows, multi-step receipt composition,
restart, stale/wrong proof, bounded pending requests, cancellation and rollback.
It does not verify live model choices, rendered meetings, purchases or teaching.
Maya still owns paired integration, linked gameplay QA and release.
