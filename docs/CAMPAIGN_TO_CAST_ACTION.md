# Campaign results can drive actual supported cast actions

The paired candidate already contains the pieces for a real result-to-action
loop. `test_campaign_cast_action.py` now exercises them together rather than
ending at a changed sentence:

1. An authenticated native-style badge snapshot is explicitly shared through the
   future-campaign setting. It is a client attestation, not a simulated battle.
2. Briney's configured author receives that exact public result and inspects an
   actual archived map. A deterministic test author chooses a retained project;
   no Briney plan, construction trigger or story branch is shipped as a preset.
3. The normal typed action compiler commits the intention, not a success event.
4. The authority refuses to alter occupied terrain. Players are never displaced
   or asked to perform the building work.
5. Once safe, the existing validated compiler commits a genuinely changed
   walkable courtyard/access route. The completion receipt cites the real badge
   observation that informed the decision.
6. That actual result can prompt the actor's next decision. Geometry and receipts
   survive restart; the action does not run twice.

This is integration validation of existing production mechanisms, not a new
construction variation. No production behavior change was needed. It proves an
abstract actor-owned project changes usable world geometry; it does not prove
Briney walked there, animated labor occurred, or a live model chose this plan.
The test never advances a trainer's story or creates a duplicate Briney object.

## What remains outside the supported boundary

Original cast native hooks currently inject bounded supplemental conversation at
reviewed safe points. They do not expose arbitrary native movement, shop service
changes, travel schedules, or scripted party replacement to the author.
Generated-world characters have separate supported movement/team adapters, but
those cannot honestly be described as original Wally/Briney/Steven travelling.

The campaign collector currently observes completed possession/progression flags,
not rival battle performance. A Wally defeat or rematch result needs a reviewed
battle-result bridge that identifies the actual trainer, result and save lineage
at the safe return to field. A badge does not supply that evidence. A later action
must then use a verified compatible native hook. Wally's original preset parties
also differ in species, IVs and explicit moves; treating those as one agent-earned
individual without a reconciliation design would be misleading.

Full native party/practice verification and rendered behavior remain Maya's
integration/QA gates. These limitations should direct the next work rather than
be papered over with more authored dialogue or invented victories.

The shared council added previously is one optional unanimous decision policy.
It is not a claim that BG3 uses universal unanimity, nor a requirement for all
future shared conversations. A speaker-led advisory mode would be a separate
explicit policy; neither should silently replace the other.
