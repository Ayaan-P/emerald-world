# Experimental world-presence batching

The authority currently broadcasts a complete recipient-specific snapshot to every connected player after every `STATE` or `FIELD` update. Native clients report around ten times per second. With many players, this multiplies snapshot generation and traffic even while everyone is stationary.

This draft keeps each authenticated player's current state and interaction eligibility up to date immediately, but batches changed presence for 50 ms before broadcasting the latest snapshot. Continued updates do not postpone that deadline. An unchanged state does not schedule another broadcast until a one-second heartbeat is due, so idle clients still receive snapshots and fresh friend TTLs. Event-driven broadcasts remain immediate and include any pending latest presence; they consume the pending batch to avoid a duplicate. Selector scheduling and load can add latency, so 50 ms is a target, not a real-time guarantee. The wire format, per-recipient relevance, save ownership and private party/bag boundaries are unchanged.

An in-memory fixture runs the production authority with 32 identities and shows 33 rapid updates resulting in one scheduled broadcast containing the latest state. It also checks idle heartbeat, friend freshness, ready-to-busy changes, and an immediate event consuming the batch. Existing link and story-rally unit suites pass. These are component tests, not a network benchmark or actual 32-client acceptance. No local socket, native client, adverse WAN, long idle/reconnect, simultaneous activity, or mixed-version gameplay test has been run here. The 50 ms batching interval may alter the timing of UI presence updates even though authority decisions see the latest state immediately.
