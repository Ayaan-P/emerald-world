# Experimental extra runtime object slots

The stock save contains exactly sixteen object events. Raising the shared constant directly would change `SaveBlock1` and make old saves unsafe. This prototype separates that fixed serialized count from an opt-in 48-entry native runtime array. `WORLD_EXTENDED_OBJECTS` defaults to 0 (opt-in Linux build: `make linux WORLD_EXTENDED_OBJECTS=1`) and this is not a release-ready or native-tested feature.

With `PORTABLE` and `WORLD_EXTENDED_OBJECTS=1`, ordinary native objects and the local player still allocate only in the original sixteen slots. The world bridge attempts to allocate remote trainers and its shared objects from 32 additional transient slots first, falling back to a free original slot if necessary. Thus a busy map can retain its normal campaign NPCs and still render some remote peers. Feature-enabled clients now negotiate a per-recipient relevance window of up to 32 peers with an updated authority, instead of eight. A new client falls back to 16 and then eight peers when older servers reject newer capabilities; legacy clients continue to receive at most eight. The default 32-player authority has at most 31 other peers per client. A second independently default-off flag, `WORLD_EXTENDED_SPRITES=1`, expands the native sprite array from 64 to 96 and uses up to 128 existing OAM entries. Sprite tile memory and palette counts are unchanged, so the number actually rendered may still be smaller. This is not a claim that a 32-player session has been rendered or played, nor of unlimited entities. The save path strips bridge actors as before, copies only the original sixteen object entries and tears down owned bridge actors before clearing transient entries on load.

The gate-on and gate-off production allocator/save and sprite allocation, OAM-list and copy-queue functions were compiled with disposable C stubs. Tests exercise allocation, full pools, duplicate identity checks, save boundaries, old save layout, clearing of transient slots, and server/handshake fixtures with 8-, 16- and 32-peer relevance windows and old-server fallback. An extracted production parser/reconciler fixture checks 16 and 32 peers alongside 16 occupied native slots, with disposable engine stubs. A separate compiler check compares the actual `SaveBlock1` size and following member offsets across both builds. Existing save isolation, native save and co-op engine component tests pass. Portable changed sources passed isolated syntax checking with placeholder generated graphics, not a game build. LeakSanitizer was disabled due to the local ptrace restriction.

Before enabling: audit all native object index assumptions, resource exhaustion, engine scripts and transitions; build the actual native client; verify old saves and new saves, dense maps, sprite/palette exhaustion, scene changes, saves, load/rejoin, native link and story scripts with real disposable clients. Test actual two-client rendering and late joins. The original sixteen-entry save format and per-trainer ownership must remain unchanged. This branch may overlap generated-cave work in `world_bridge.c` and `event_object_movement.c`; reconcile against the integration candidate. On commit c72f700, CI passed the earlier 32-object/16-peer prototype with both experimental gates enabled, its gate-on headless frame/save smoke, the default-off baseline and focused regressions. The current 48-object/32-peer revision requires a fresh native build and smoke. No gate-on graphical rendering, real multiplayer, or interactive save/reload test has run here.

The experimental wire roles append `PEER32` or `PEER16` to an authenticated presence capability; it does not grant control, link or host privileges. Integration with #168 must reconcile its independent cave-capability suffix and bridge edits. Remote local IDs use 160–199 in the expanded mode to avoid the stock Berry Blender reserved IDs; map/live object collisions are still checked.

## Experimental sprite pool

`make linux WORLD_EXTENDED_OBJECTS=1 WORLD_EXTENDED_SPRITES=1` enables both experiments. The second flag increases the runtime sprite array and frame-copy queue from 64 to 96 and the default OAM limit from 64 to 128, within the existing 128-entry OAM buffer. It does not increase tile VRAM, palette slots or affine matrices, and some game scenes may have hidden assumptions about sprite IDs. The GBA build and default portable build retain 64. Component tests exercise sprite allocation/exhaustion, OAM iteration, copy queue bounds and actual header/OAM sizes; no graphics, animation or resource-stress acceptance has been run.
