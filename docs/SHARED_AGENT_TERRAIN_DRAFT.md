# Durable shared terrain overlays (experimental)

An authorized owner agent can publish an additive terrain patch for the active generated event area with `python -m world.shared_terrain_control --admin-socket /path/to/owner.sock --area AREA_SHA256 --tiles-file patch.json`. The JSON is an array of 1–64 `{ "x": 5, "y": 5, "terrain": "grass" }` entries; `tall_grass` is also supported. The authority validates the entire request, merges it into a canonical overlay of at most 512 distinct tiles and commits a monotonic revision in the local world's SQLite database. The active event area must already be published with generated-area persistence and archiving enabled. A repeated identical patch is a no-op. Overlays are keyed by the immutable area identity and survive an owner-world restart. The geometry interface can remove entries or replace/reset the complete overlay.

Both allowed terrain types remain walkable. The authority and client independently reject blocked, NPC, entrance, exit-approach, exit, duplicate or malformed coordinates. Tall grass uses normal wild-encounter behavior and relies on the separate empty-party crash fix. No collision, world art, buildings, trainer save, inventory or published area identity changes.

Compatible CAVE9T clients receive a validated full overlay snapshot with the area and stage it before entry. Owner updates are queued to compatible clients that acknowledged the active area, and the latest full snapshot supersedes older live updates. A client in a script, battle or movement waits until gameplay is ready. Clients connecting later receive the stored snapshot. Separate per-trainer paint commands may intentionally override tiles for an individual, so views can still differ when those commands are used. Older CAVE9 clients cannot enter an area with a nonempty overlay; an update is refused while an incompatible trainer is known to be inside, and previously admitted incompatible clients outside are reset. Offers from an earlier revision must be fetched again rather than acknowledged after an update. A connection can still be lost after queueing, so the owner's response reports queued and post-commit delivery failures, not that clients applied them. Queue-capacity checks happen before the durable commit; a post-commit delivery failure closes the affected connection so it can fetch the persisted snapshot again. Reconnecting fetches the persisted snapshot. Entry/return races and peer-capacity integration issues remain.

This is a bounded shared grass/tall-grass overlay, not general-purpose tilemap generation, geometry editing, a synchronized arbitrary scene graph, infinite capacity or automatic graphical acceptance. Component tests exercise the actual authority, SQLite restart, protocol parser, native staging/bridge and compatibility handling in memory. No actual local socket, live two-client game, external agent or graphical tile acceptance was performed. Inspect exact-head CI before integration.


## Agent observation and client reports

`python -m world.shared_terrain_control --admin-socket /path/to/owner.sock --area AREA_SHA256 --inspect` returns the active area's 63×63 immutable walkability rows, character positions, current durable revision and overlay tiles, plus connected admitted trainers' compatibility, inside status and their last reported phase for the current revision. A compatible native client reports `staged` after validating and staging the overlay before entry and `applied` after applying it in its current map; the authority reports `pending` until a current-revision report arrives. Reports are from the authenticated client, not tamper-proof proof or graphical acceptance. A disconnect, changed revision or new offer can return a trainer to pending; targeted per-player paint can intentionally diverge after a report. No status is inferred for a disconnected trainer, and there is no automatic resend or acknowledgment guarantee.


## Connected geometry edits while the area is empty

`python -m world.shared_terrain_control --admin-socket /path/to/owner.sock --area AREA_SHA256 --geometry --tiles-file patch.json` lets an owner agent turn eligible interior cells into `grass`, `tall_grass` or blocked `water`, including opening previously blocked cells. The authority applies the complete proposed overlay to a projected map, rejects disconnected walkable land or isolated characters, and protects the entrance, exit approach, exit, perimeter and NPC tiles. It refuses collision-changing geometry edits while any trainer is known to be inside the generated area. Existing admissions and in-flight offers are reset; compatible clients fetch and validate the new revision before reentry. Authority position validation and native collision use the same projected geometry. As with the existing admission system, an entry that has begun but has not yet been reported is a remaining integration race and needs real multiplayer validation.

Geometry requires CAVE9G. Older CAVE9T and CAVE9 clients cannot enter when the overlay changes collision, and the client independently validates connectivity and NPC reachability before staging. Live updates while trainers are inside remain limited to grass/tall-grass changes on already walkable cells; the client rejects a live snapshot that changes collision. The persisted overlay supports up to 512 active entries; entries can be restored or the complete overlay replaced. Agent inspection adds `effective_rows` and each trainer's geometry capability. No actual local socket, live two-client game, external agent or graphical acceptance has been performed; check exact-head CI. Tall grass still relies on the separate empty-party crash fix.


## Replace or reset the overlay

While the generated area is empty, `--geometry --replace --tiles-file patch.json` replaces the entire overlay after validating the resulting connected map. An empty JSON array resets the overlay to the original generated geometry; the durable revision still advances. In normal geometry patch mode, an entry with `"terrain": "original"` removes that cell's override. Existing admissions and in-flight offers are reset before clients reenter. A positive revision with an empty overlay requires CAVE9G because earlier CAVE9T clients do not accept that encoding. This is a bounded replacement interface, not live collision editing while players are present. No actual local socket, live two-client game, external agent or graphical acceptance was performed.


## Larger agent-authored overlays

CAVE9H extends the durable shared overlay from 64 to 512 cells within the existing 63×63 area. A full `--geometry --replace` JSON document can contain up to 512 cells; the CLI compacts larger requests over the existing owner-only channel. Collision-changing geometry still requires everyone to leave, and the complete projected map is checked for connectivity and character reachability. Ordinary live grass/tall-grass patches remain limited to 64 cells per request, but can build an overlay up to 512 entries. The larger canonical snapshot is split into ordered bounded frames and applied only after the complete snapshot is received and independently validated. The authority validates compact owner input; the native client rejects malformed, truncated, duplicated or out-of-order snapshot chunks. Old CAVE9G/T clients cannot enter an area with more than 64 active entries; crossing that threshold while an incompatible trainer is known to be inside is refused. Existing outside admissions are reset, and newer clients negotiate down with older hosts.

This increases editable cells, not the physical 63×63 map footprint. It does not permit live collision changes while trainers are inside, remove the remaining entry/return race, create new artwork or prove real two-client behavior. Reports remain client-reported rather than tamper-proof. No actual local socket, external agent, real two-client game or graphical tile acceptance was performed.
